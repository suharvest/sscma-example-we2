# Himax WE2 Face Embedding Consistency Debug

## Current Finding

The earlier conclusion that v2_lfw6 diverged at the first Conv2D was incorrect.
The compare script was using `FACEDBG.emb_input.data_b64` after invoke. On TFLM,
the arena can reuse the input tensor buffer after the model runs, so the dumped
input may no longer be the original input. For fixed-input tests, local CPU
comparison must reconstruct the input from `fixed_test_seed`.

`tools/compare_facedbg_tensor.py` now defaults to seed reconstruction when
`fixed_test_seed` is present. Use `--prefer-dumped-input` only when the firmware
captures an input snapshot before invoke.

buffer and produced a false failure.

## MRE Status

`tools/make_himax_conv2d_mre.py` generates tiny Conv2D MRE models. The first
attempted MRE (`Conv2D -> 1x1 projection`) is no longer considered a device bug:
with corrected fixed input, WE2 output matches local TFLite exactly.

## w600k_stage80_unlock_lfw_a Status

`w600k_stage80_unlock_lfw_a` is not aligned enough for a workflow where the
enrollment vector is generated by local CPU TFLite and the recognition vector is
generated on Himax WE2. With fixed seed 7 and the same INT8 input:

| Probe | Tensor | Result |
| --- | --- | --- |
| full model | 128D embedding | FAIL, max_abs=12, cosine=0.970066 |
| `op20_proj8` | first residual add, first 8 channels | PASS, max_abs=2, cosine=0.999851 |
| `op26_proj8` | residual add before suspect block | PASS, max_abs=3, cosine=0.999673 |
| `op27_proj8` | `Conv27` output, first 8 channels | PASS, max_abs=3, cosine=0.999750 |
| `op28_proj8` | `PReLU28` output, first 8 channels | PASS, max_abs=5, cosine=0.999740 |
| `op29_proj8` | `DepthwiseConv29` output, first 8 channels | FAIL, max_abs=4, cosine=0.998623 |
| `op30_proj8` | `PReLU30` output, first 8 channels | FAIL, max_abs=6, cosine=0.998507 |
| `op31_proj8` | `Conv31` output, first 8 channels | FAIL, max_abs=3, cosine=0.998828 |
| `op32_proj8` | next residual add, first 8 channels | FAIL, max_abs=4, cosine=0.999483 |

The first clearly amplified mismatch is around:

```text
op27 Conv2D -> op28 PReLU -> op29 DepthwiseConv2D -> op30 PReLU -> op31 Conv2D -> op32 Add
```

`op27` and `op28` already carry small CPU-vs-device rounding differences, but
`op29` is where the divergence becomes large enough to fail the current
cross-runtime tolerance. The full embedding cosine then drops to about `0.97`,
which is high for two arbitrary face embeddings but too low for "same input,
same model, different runtime" consistency.

Further split testing refined the conclusion:

| Test | Input | Result |
| --- | --- | --- |
| Original prefix through `op29` | fixed 112x112x3 seed 7 | Runs, mismatch appears at `op29` |
| Dirty slice `op27..op29` Vela | CPU `op26` tensor from flash | Device reboots |
| Dirty slice `op29` Vela | CPU `op28` tensor from flash | Device reboots |
| Clean standalone `op29` Vela | CPU `op28` tensor from flash | Device reboots |
| Clean standalone `op29` non-Vela | CPU `op28` tensor from flash | Fails allocation: CPU `DEPTHWISE_CONV_2D` is not registered |

This means the safe statement is narrower than "DepthwiseConv2D is buggy":
the mismatch concentrates at the `op28 -> op29` boundary, and `op29`
DepthwiseConv2D is the first point where the existing full-prefix execution
amplifies the difference. However, a standalone `op29` Vela MRE currently
reboots the device instead of producing a comparable tensor, so it is not yet a
valid numerical MRE for an upstream bug report. It is still a useful runtime
MRE showing that tiny single-op Vela models with a `[1,28,28,80]` int8 input can
hit a WE2 runtime failure.

During this split testing, `FACEEMBFLASH` was also fixed to be generic. The old
command passed `ALIGNED_FACE_BUFFER_SIZE` (`112*112*3`) as the input size, so it
could only test normal face-aligned RGB input models. It now uses the current
model input tensor byte count when the passed size is `0` or stale, which allows
flash-fed intermediate-tensor tests such as `[1,28,28,80]`.

Additional `op29` channel-window probes were run because full 80-channel
projection models rebooted the device while 16-channel windows were stable.
Each window uses the same prefix graph through `op29` and a final 1x1 projection
that selects 16 output channels:

| Probe | Channels | Result |
| --- | ---: | --- |
| `op28_proj16` | 0..15 | PASS, max_abs=5, mean_abs=0.4438, cosine=0.999684 |
| `op29_proj16` | 0..15 | PASS, max_abs=4, mean_abs=0.3193, cosine=0.999076 |
| `op28_proj16_ch16` | 16..31 | PASS, max_abs=5, mean_abs=0.4780, cosine=0.999502 |
| `op29_proj16_ch16` | 16..31 | FAIL, max_abs=5, mean_abs=0.3325, cosine=0.998358 |
| `op29_proj16_ch32` | 32..47 | PASS, max_abs=3, mean_abs=0.2690, cosine=0.999146 |
| `op29_proj16_ch48` | 48..63 | PASS, max_abs=4, mean_abs=0.3587, cosine=0.999727 |
| `op29_proj16_ch64` | 64..79 | PASS, max_abs=3, mean_abs=0.3251, cosine=0.999191 |

The most suspicious channel window is therefore `op29` channels `16..31`.
Within all `op29` windows, the largest mean per-channel differences were seen at
global channels `61`, `46`, `30`, `67`, `7`, and `59`. The only failing 16-wide
window was `16..31`; in that window, global channel `30` is the strongest local
outlier. This makes a channel-window MRE more practical than trying to ship the
full original model as an upstream reproducer.

Channel 30 was then isolated by patching the projection weight buffer so output
slot 0 selects global channel 30 and output slots 1..15 are zero projections:

| Probe | Selected channel | Slot-0 Result | Full Output Result |
| --- | ---: | --- | --- |
| `op28_proj16_ch30only` | 30 | max_abs=5, mean_abs=0.6633, nonzero=305/784 | FAIL, cosine=0.998737 |
| `op29_proj16_ch30only` | 30 | max_abs=3, mean_abs=0.5740, nonzero=394/784 | FAIL, cosine=0.997164 |

The zero projection slots match exactly, so the mismatch is not caused by the
final debug projection itself. Channel 30 is already a single-channel outlier at
`op28`; the wider 16-channel window only starts failing the current cosine
tolerance at `op29`. That means `op29` is still the first failing multi-channel
boundary, but the minimal reproducer should include both `op28` and `op29`
channel-30 probes to show whether WE2/Vela is accumulating small channel-local
rounding differences before the depthwise block.

The `op29` channel-30 weight scale is not extreme: it ranks 44/80 by weight
scale. Focus-channel effective multipliers were:

| Channel | `op29` weight scale | Effective multiplier |
| ---: | ---: | ---: |
| 30 | 0.013513 | 0.003328 |
| 61 | 0.019470 | 0.004796 |
| 46 | 0.014433 | 0.003555 |
| 67 | 0.021397 | 0.005270 |
| 7 | 0.031775 | 0.007826 |
| 59 | 0.025205 | 0.006208 |

This weakens the hypothesis that channel 30 is failing simply because its
per-channel weight scale is unusual. The next useful MRE should preserve the
real upstream activation distribution for channel 30.

A self-contained MRE package is available at:

```text
artifacts/himax_w600k_ch30_mre/
```

It includes the `op28` and `op29` channel-30-only TFLite/Vela models, the WE2
FACEDBG captures, CPU reference tensors, and `scripts/analyze_ch30.py`. The MRE
keeps the real prefix from fixed input through `op27 -> op28 -> op29`; it is not
a random-input standalone depthwise model.

`analyze_ch30.py` also groups the device-vs-CPU differences by CPU op27
channel-30 sign around zero point `-12`:

| Probe | Negative-region mean abs | Positive-region mean abs |
| --- | ---: | ---: |
| `op28_ch30only` | 0.6906 | 0.6213 |
| `op29_ch30only` | 0.5718 | 0.5733 |

The mismatch is therefore not isolated to PReLU28's negative branch. A fix based
on an explicit `op28 -> op29` quantization boundary or recalibrating the op28
output/op29 input tensor is more promising than replacing PReLU outright.

## Boundary And Recalibration Experiments

Two direct graph-surgery experiments were run on the channel-30 MRE:

| Experiment | Probe | Result |
| --- | --- | --- |
| A: explicit `QUANTIZE` after `op28` with original tensor-167 qparams | `op29_ch30` | No change: max_abs=3, mean_abs=0.5740, cosine=0.997164 |
| B: tensor-167 scale `0.002983 -> 0.0014915` | `op29_ch30` | Worse: mean_abs=0.5918, cosine=0.996627 |
| B: tensor-167 scale `0.002983 -> 0.005966` | `op29_ch30` | Local PASS by cosine: mean_abs=0.5982, cosine=0.999455 |
| B: tensor-167 scale `0.002983 -> 0.004712` | `op29_ch30` | Local PASS by cosine: mean_abs=0.5599, cosine=0.999130 |

The explicit boundary was compiled by Vela as a full NPU model
(`CPU operators = 0`) but did not change device-vs-CPU output. A plain identity
quant boundary is therefore not enough.

The two locally promising recalibration variants were then applied to the full
embedding model and tested with fixed seed 7:

| Full Model Variant | Full Embedding Result |
| --- | --- |
| tensor-167 scale `0.004712` | FAIL, max_abs=11, mean_abs=2.8750, cosine=0.973331 |
| tensor-167 scale `0.005966` | FAIL, max_abs=16, mean_abs=4.0391, cosine=0.965706 |

This rejects the simple tensor-167 scale-only fix. It can improve the isolated
channel-30 cosine, but it does not recover the full embedding to the required
`~0.999` range. The next fix attempt should either target a broader subgraph
(`op27 -> op32`) with consistent recalibration across adjacent tensors, or avoid
this block pattern in the production embedding model.

Avoid using this model for CPU-enroll/device-recognition unless enrollment is
also performed by the same WE2 runtime. For mixed-runtime enrollment, prefer a
model that passes the fixed-seed device-vs-CPU check end to end, such as the
verified `iddistill_v2_lfw6` path. If this model family must be kept, retrain or
export a WE2-friendly variant that avoids the PReLU-heavy inverted residual
blocks, or validate a graph-surgery variant replacing PReLU with a simpler
activation before doing recognition threshold calibration.

## WE2-Friendly Activation Replacement Trial

To reduce the suspect block divergence without changing the rest of the official
W600K stage80 topology, four variants were trained from
`w600k_stage80_unlock_lfw_a/w600k_stage96_pairft.weights.h5` with `keep_channels=80`:

| Variant | Changed activations | Vela SRAM | CPU ops | LFW Acc | LFW TAR@FAR1 | CFP-FP TAR@FAR1 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `unlock_a` baseline | none | `735.09 KiB` | 0 | 92.2% | 83.3% | 2.7% |
| `we2_leaky` | `PRelu_28`, `PRelu_30` -> LeakyReLU | `735.09 KiB` | 0 | 90.6% | 61.7% | 1.5% |
| `we2_relu6` | `PRelu_28`, `PRelu_30` -> ReLU6 | `735.09 KiB` | 0 | 88.3% | 65.8% | 2.8% |
| `we2_prelu28_leaky_a` | `PRelu_28` -> LeakyReLU | `735.09 KiB` | 0 | 88.3% | 67.5% | 3.4% |
| `we2_prelu30_leaky_a` | `PRelu_30` -> LeakyReLU | `735.09 KiB` | 0 | 87.8% | 71.7% | 3.1% |

All variants compile fully to Ethos-U (`CPU operators = 0`) and stay under the
`760 KiB` SRAM target. However, every activation-replacement variant loses too
much LFW strict-FAR performance compared with the baseline. This path is
therefore not a good production candidate unless a later device consistency test
shows a dramatic improvement that justifies the accuracy drop.

The more promising next step is a smaller graph/runtime investigation: keep the
official PReLU behavior for accuracy, then isolate whether the mismatch is due
to a specific `PReLU -> DepthwiseConv2D` quantization pattern, residual add
scaling, or Vela/operator scheduling detail. Do that with fixed-input probe
models before training more replacement variants.

```bash

  --source-json /tmp/tflite_surgery/mfn_w1_pairft_128d.int8.json \
  --out-dir /tmp/we2_conv2d_mre \
  --variant channel0 \
  --with-projection \
```

top-level `fixed_test_seed`. If a capture lacks the seed, only use it with
`--prefer-dumped-input` when the firmware is known to snapshot the input before
